0000 智能建造大模型预测技术说明
0001 预测链路、LangChain / LangGraph 与 RAG 落地方案
0002 整理日期：2026 年 9 月 30 日
0003 文档依据：当前项目代码梳理及本次技术讨论。本文区分当前主链路、仓库已有模块与后续建设建议；不代表已经完成真实数据预测效果验证。
0004 一、系统定位与实现边界
0005 系统以智能建造技术主题和 IPC 专利演化证据为输入，通过 LangGraph 编排大模型完成预测、评审、修正、路线图与综合分析。后续通过 RAG 接入可追溯的论文、专利与项目材料，并结合独立定量模型增强预测的证据基础。
0006 当前页面调用简化版预测链路。仓库还保留传统三轮预测、LangChain 适配器、证据检索和研究工作流模块，但这些能力没有全部接入当前 API。README 中描述的能力不能直接等同于当前页面已经启用的能力。
0008 二、当前实际运行的端到端链路
0009 2.1 总体流程与技术栈
0010 React 前端发起预测 → FastAPI 创建任务 → 后台线程读取主题证据 → LangGraph 执行预测与评审 → 按需修正 → 生成路线图与综合结论 → 保存 JSON → 前端轮询展示。
0012 主要入口：src/api/app.py、src/forecast/service.py、src/forecast/graph.py。
0013 2.2 输入阶段：读取预先整理的证据
0014 当前 API 创建任务时不接收自定义研究材料，而是读取 data/seed/topics.json。每个主题主要包含 topic_name（技术主题）、keywords（关键词）、example（典型场景）和 ipc_trend（IPC 专利网络演化摘要）。
0015 例如，“机器人集群协同”的摘要已写入机器人相关 IPC 的中心度变化、共现关系和潜在融合方向。当前大模型使用的是已经整理好的摘要文本，主链路不会在执行时重新读取原始专利、计算网络指标或检索论文。
0016 因此，预测质量首先取决于摘要是否准确、完整、及时，以及是否能追溯到原始数据。
0017 2.3 Execute：逐主题预测
0018 执行器将主题、关键词、场景和 IPC 摘要填入提示词，要求输出驱动因素、2030—2035 年关键瓶颈、到 2040 年可能实现的突破、使能技术、置信度和不确定性。
0019 各主题独立调用模型，最多使用 5 个线程并行执行。该方式适合相对独立的主题分析，能够减少等待时间并保留各主题的结构化产物。
0020 2.4 Think：科学评审
0021 评审节点接收原始证据摘要和初次预测，检查证据是否被过度外推、是否存在绝对化表述、瓶颈与突破是否可信，以及置信度是否合理。输出包括问题列表、严重程度和修正建议。
0022 Execute、Think 等角色主要通过不同提示词实现，当前调用相同模型配置，不能理解为多个独立训练的专家模型。
0023 2.5 Revise：有限次数修正
0024 任何主题出现 medium 或 high 严重程度问题时，流程进入修正节点。当前触发修正后会重新生成全部主题预测，最多修正一次；修正后直接进入路线图节点，不再次评审。
0025 目前形成的是有界的一轮评审与修正机制，尚未形成持续补充证据并反复验证的完整闭环。
0026 2.6 Roadmap：生成分阶段路线图
0027 每个主题生成 2030、2035、2040 三个阶段的里程碑，附带 TRL 技术成熟度（1—9）、不确定性等级、里程碑说明及终期成熟度。
0028 TRL 当前由模型依据材料判断。正式研究应说明每一等级对应的实验、示范或产业化证据，不能仅依据模型输出确认成熟度。
0029 2.7 Synthesize：跨主题综合
0030 综合节点汇总各主题的突破、置信度和不确定性，提炼智能建造新范式、跨主题融合方向、重大挑战与综合结论。
0031 当前实际输入为主题预测摘要，未包含前一步完整路线图。若希望识别跨主题里程碑依赖，需补充路线图输入。
0032 2.8 任务状态与持久化
0033 后端保存任务状态和最终结果，前端轮询获取。任务服务主要在开始、完成和失败时写状态，图内各节点进度尚未逐步同步到任务文件。
0034 当前预测图未配置持久化 checkpointer，因此当前页面链路不具备完整的节点级恢复能力。其他研究模块中的检查点实现需要单独接入和验证。
0035 三、预测方法与关键技术
0036 3.1 三类计算的职责
0038 大模型擅长组织技术语义。例如，从机器人与感知、通信技术联系增加，解释多机器人协作的技术基础，再识别非结构化环境、安全和调度瓶颈，形成阶段性情景。但从“共现增加”到“未来实现突破”包含假设，必须明确标注。
0039 3.2 定量融合预测
0040 研究模块的计算链路为：专利—IPC 归属数据 → 按时间构建 IPC 共现网络 → 构建候选 IPC 对 → 提取特征 → 训练模型、比较基线并进行时间验证 → 输出排名、校准概率和不确定性。
0041 特征包括共同邻居、Adamic–Adar、资源分配指标、优先连接、节点度变化、边强度变化，以及专利和论文信号。模型模块包含逻辑回归、决策桩、基线比较与 Platt 校准相关实现。
0042 相关代码为 src/research/features.py 和 src/research/models.py。当前简化 API 未调用这条链路。模块存在不代表已经在真实数据上取得有效预测成绩，仍需检查训练、验证和校准产物。
0043 建议职责分工：定量模型给出受数据约束的分数、排名和概率；大模型解释技术含义，并生成带有假设和边界的情景。大模型不能随意改写定量结果。
0044 3.3 置信度必须区分含义
0046 当前主链路 confidence 是模型生成的 0—100 数值。旧版自洽性模块使用多次输出的相似程度计算一致性，其中包含文本相似度方法。这两者都不能直接解释为未来发生概率，不能将“自评分 85”表述为“准确率 85%”。
0047 四、LangChain 与 LangGraph 的作用
0048 4.1 两者的分工
0049 LangChain 主要解决组件组合，统一提示词、模型接口、检索器和结构化输出。LangGraph 主要解决流程与状态管理，用节点、边和共享状态表达多步骤任务；持久化恢复仍需配置检查点机制。[1]
0051 项目锁定 langchain-core==0.3.84、langgraph==0.2.55。后续接入应按这组依赖检查兼容性，不能直接假设新版示例可原样运行。
0052 4.2 当前接入方式
0053 src/forecast/graph.py 直接使用 StateGraph、节点函数、条件分支和 ForecastState。模型调用仍由 requests 完成，没有经过仓库中的 LangChain 适配器。
0054 准确表述是：当前系统使用 LangGraph 编排预测流程，使用自定义 HTTP 客户端调用大模型。
0055 4.3 已有 LangChain 适配器
0056 src/research/langchain_adapter.py 将原有客户端封装为 BaseChatModel，利用 ChatPromptTemplate 加载角色提示词，通过 RunnableLambda 实现结构化输出降级处理，并保存提示词版本、校验和及模型配置清单。
0057 适配器还校验证据 ID、IPC、预测年份与科学措辞，对输出错误执行有限次数纠正，可作为后续整合基础。
0058 重新接入前需核对配置是否真正传递给底层客户端：当前默认构造 LLMClient()，清单中的模型名不自动等于实际调用的模型名。
0059 4.4 结构化输出的边界
0060 当前主链路采用“请求 JSON → 解析 JSON → Pydantic 校验”。这可以检查字段、类型和范围，但不能证明内容真实。
0061 目前提示词未完整注入输出 Schema。模型可能返回合法 JSON，却因缺少字段而校验失败。后续应明确提供字段说明或 JSON Schema，并保留业务校验。提供方原生结构化输出和工具调用等策略的可用性取决于具体模型与集成实现。[2]
0062 五、现有检索能力与 RAG 差距
0063 RAG（检索增强生成）的核心是：针对任务检索外部证据 → 将证据放入上下文 → 模型基于证据生成结果。RAG 不要求所有数据进入向量库，已有 SQL 数据库也可以成为检索来源；向量检索主要用于语义相关文本召回。[3]
0064 5.1 已有证据检索服务
0065 src/retrieval/service.py 的 EvidenceRetrievalService 能从主题和材料提取 IPC，按项目范围选择数据集，查询 IPC 年度指标和融合记录，搜索论文，并合并项目材料与阶段分析结果。服务会为证据生成稳定 ID，形成证据包并检查质量。
0066 当前论文搜索主要通过 SQL LIKE 匹配标题、摘要、关键词和作者，再由检索服务排序。它还不是完整的全文语义检索路径。
0067 5.2 待补齐的环节
0069 优先让预测真正使用现有证据库并建立引用关系，再优化语义检索效果。
0070 六、RAG 落地方案
0071 以下内容是针对项目的建设建议，不是当前已完成功能。建议采用“结构化查询＋文本混合检索＋证据评审”的架构。
0072 6.1 离线与在线两条链路
0073 离线入库：论文、专利全文和材料 → 解析清洗 → 保留来源与时间 → 语义切分 → 关键词索引与向量索引。IPC 指标和模型产物分别进入结构化数据库。
0074 在线预测：研究主题、截止时间和技术范围 → 查询规划 → 多路召回 → 去重与重排 → 定量和文本证据包 → 质量检查与冻结 → 预测 → 引用及科学评审 → 按需补检索 → 路线图与报告。
0075 6.2 数据入库与元数据
0077 文件处理建议为：上传 → 去重 → 文本提取 → 质量检查 → 必要时 OCR → 章节和页码识别 → 切分 → 建索引。
0078 每个片段至少保留 document_id、chunk_id、source_type、title、DOI 或专利标识、published_at、available_at、page、section、ipc_codes、technology_ids、dataset_id、dataset_version、content_hash 和 text。
0079 published_at 表示发表时间，available_at 表示实际可获得时间。历史预测必须按当时可获得的信息截断。
0080 6.3 切分策略
0081 论文按章节与段落切分，保留实验结果和局限性。专利区分摘要、权利要求和实施方式，避免将权利要求覆盖范围等同于已实现性能。表格保留表头、单位、年份及注释，防止数字与含义脱离。
0082 可从每块约 400—800 tokens、少量重叠开始实验，再按检索评估调整。这是初始配置，不是固定最优值。
0083 6.4 查询规划
0084 以“机器人集群协同”为例，应把预测任务拆为证据问题，而不只搜索主题名称。
0086 可扩展中英文同义词，但不得改变原定技术范围和时间范围。
0087 6.5 多路召回、融合与重排
0088 结构化查询精确获取 IPC、年份、样本量、指标与模型结果；关键词检索处理编码、术语和精确短语；向量检索处理同义表达、跨语言与语义相近文本。三路结果汇总后去重、融合排名并重排。
0089 可以从每路召回几十条、重排后保留少量高价值片段开始实验。最终上下文数量由相关性、覆盖度和 token 预算共同决定。
0090 不能直接平均向量相似度、关键词得分与模型概率，它们的量纲与含义不同。可先使用基于名次的融合方法，再由评测决定是否采用更复杂策略。
0091 6.6 证据包与反证
0092 证据包应围绕预测命题组织，同时包含 observed_trends、quantitative_results、supporting_evidence、contradicting_evidence、limitations 和 evidence_ids，并绑定主题与 cutoff_date。
0093 必须区分观测事实、定量结果、支持材料、反证或限制以及未解决缺口。同一论文的多个片段不能视作多个独立来源，转载与重复摘要也要去重。
0094 6.7 逐条结论引用
0095 建议将自由文本突破列表升级为命题结构：claim（结论）、claim_type（事实、外推或情景）、target_year、supporting_evidence_ids、contradicting_evidence_ids、assumptions 和 uncertainty。
0096 例如：“在限定施工场景中，多机器人协同应用可能扩大”，可标记为 2035 年情景，绑定支持证据 E12、E31 与反证 E44，明确假设为现场定位和安全机制达到部署要求，不确定性为 high。此例仅用于说明结构，不代表已有实证结论。
0097 前端可以从结论回溯原文，系统也能自动检查引用。输出应明确区分观测事实、合理外推、情景假设与证据不足。检索内容属于资料，不能用其中的指令覆盖系统预测规则。
0098 6.8 引用与科学性校验
0100 真实来源不一定支持当前结论，因此不能只检查引用 ID 存在。发现缺口时可允许最多一到两轮补检索，记录新旧证据快照；仍缺乏支持的结论应降级为情景假设或明确标记证据不足。
0101 6.9 接入现有 LangGraph
0102 建议节点顺序为：prepare → plan_queries → retrieve → rerank → validate_evidence → freeze_snapshot → execute → think → 按需补检索或修正 → validate_claims → roadmap → synthesize → persist。
0104 可从替换 ipc_trend 单一摘要输入开始，无需为了 RAG 重写整个项目。
0105 七、时间约束、评估与成本
0106 7.1 时间泄漏防控
0107 技术预测只能使用预测时点已存在且可获得的证据。模拟在 2020 年预测时，检索不得返回后续材料，网络特征只能使用截止前的数据，IPC 映射、候选定义和数据版本应冻结。未知发表时间的材料不能自动成为合格历史证据。
0108 现有论文查询允许 year IS NULL 记录进入结果，正式回溯中应单独复核或排除。
0109 过滤检索库不能消除大模型参数中潜在的未来知识。使用新模型做历史回测时应披露这种污染可能，将严格定量回测与大模型解释质量分开报告，不能只凭提示词就宣称无时间泄漏。
0110 仓库部分旧工作流采用 2026 基线，当前预测结果和研究 v3 采用 2025 基线。整合前应统一截止日、基线年、预测节点以及部分年度处理方法。
0111 7.2 三层评估体系
0113 Brier 和概率校准适用于明确事件及概率输出，不适用于任意未来展望文本。
0114 建议比较四组：A 为现有固定摘要；B 接入关键词检索；C 增加向量召回和重排；D 增加反证与受控补检索。在相同主题、截止时间和输出结构下，比较证据质量、专家评价、成本及延迟，识别真正贡献效果的环节。
0115 7.3 模型调用成本
0116 不计重试时，N 个主题的当前调用量为：无修正 3N＋1 次（预测、评审、路线图各 N 次，综合 1 次）；触发修正 4N＋1 次。9 个主题约为 28—37 次。
0117 接入 RAG 后应优先使用确定性检索、缓存和证据去重，仅对存在问题的主题追加调用，避免各阶段反复处理整份材料。
0118 八、分阶段实施路线
0120 项目介绍或论文可采用以下表述：系统采用证据约束的多阶段技术预测方法，以 IPC 网络演化与领域文献为信息基础，利用 LangGraph 编排主题预测、科学评审、修正与路线图生成。后续通过 RAG 将可追溯外部证据动态注入预测上下文，并结合独立技术融合模型、时间回溯验证及人工复核，评估预测结论的依据、边界与不确定性。
0121 在 RAG、定量模型和持久化研究流程接入当前主链路并完成验证前，应将其明确标注为后续建设内容。
